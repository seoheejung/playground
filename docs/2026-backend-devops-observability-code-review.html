✓
Kafka offset commit 전략 — at-least-once 보장 잘된 점 ▾

ENABLE_AUTO_COMMIT_CONFIG = "false"로 자동 커밋을 끄고, batch 전체 성공 시에만 consumer.commitSync()를 호출합니다. write 실패 시 커밋을 생략해 Kafka가 같은 메시지를 다시 전달하게 만드는 at-least-once 보장 패턴을 정확하게 구현했습니다.

특히 allSucceeded = false로 하나의 실패가 전체 batch commit을 막는 구조는 부분 성공 / 부분 유실 시나리오를 원천 차단합니다.

SIGTERM 수신 시 writer.flush()와 writer.writeCollectorStats()를 호출해 메모리 버퍼의 미전송 데이터를 최대한 보존합니다. 배포/재시작 시 메트릭 손실을 최소화하는 운영 관점에서 세심한 처리입니다.

400/401/403 응답은 재시도해도 동일하게 실패합니다. 이 케이스를 명시적으로 return false로 즉시 포기 처리해 exponential backoff 대기 시간 낭비와 Kafka lag 증가를 방지한 설계가 실용적입니다.

!
InfluxWriter — Thread-safety 미보장 개선 포인트 ▾

InfluxWriter의 buffer(mutableListOf)와 lastFlushAt은 동기화 없이 공유됩니다. 현재 단일 스레드(KafkaConsumer.run()) 구조에서는 문제 없지만, 향후 멀티 파티션 병렬 처리 등으로 확장 시 레이스 컨디션이 발생할 수 있습니다.

Kotlin의 @Synchronized 어노테이션이나 java.util.concurrent.CopyOnWriteArrayList로 방어하거나, 단일 스레드 전제임을 명시적 주석으로 문서화하는 것을 권장합니다.

!
Blocking retry — Kafka poll 차단 개선 포인트 ▾

Thread.sleep(waitMs) 방식의 동기 retry는 KafkaConsumer 루프 전체를 블로킹합니다. 최대 3회 재시도(1s+2s+4s = 7초)동안 Kafka에서 새 메시지를 수신할 수 없어 consumer lag가 쌓입니다.

비동기 처리(코루틴 또는 별도 스레드풀)나 최소한 retry 횟수 축소, 혹은 실패 즉시 dead-letter 처리 후 계속 consume하는 전략을 고려할 수 있습니다.

!
kafkaLag = 0 하드코딩 개선 포인트 ▾

CollectorMetrics.kafkaLag이 0으로 고정되어 Grafana에 노출되는 Collector Stats의 kafka_lag 값이 의미 없습니다. 파이프라인 병목 진단에 핵심 지표인 만큼 AdminClient로 실제 lag을 조회하거나, 0임을 대시보드에서 명시하는 처리가 필요합니다.

# WSL2 Mini PC에 등록한 self-hosted runner에서만 실행 runs-on: self-hosted # Nginx runtime 파일 고정 경로로 복사 + SSL 자체서명 인증서 자동 생성 - name: Prepare Nginx runtime files run: | cp nginx/nginx.conf /home/gali/nginx/nginx.conf cp nginx/conf.d/gitlab.conf /home/gali/nginx/conf.d/ if [ ! -f /home/gali/nginx/ssl/gitlab.local.crt ]; then openssl req -x509 -nodes -days 365 -newkey rsa:2048 \ -keyout /home/gali/nginx/ssl/gitlab.local.key \ -out /home/gali/nginx/ssl/gitlab.local.crt \ -subj "/CN=gitlab.local" fi # GitLab + Nginx / Monitoring 별도 compose로 분리 배포 - name: Deploy GitLab and Nginx containers env: MINI_PC_HOST: ${{ secrets.MINI_PC_HOST }} run: | docker compose \ -f infra/compose/docker-compose.gitlab.yml \ up -d --remove-orphans - name: Deploy Monitoring containers run: | docker compose -p monitoring \ -f infra/compose/docker-compose.monitoring.yml \ up -d --remove-orphans

✓
GitHub-hosted runner 우회 설계 — 현실적 제약 해결 잘된 점 ▾

공용 인터넷에서 사설 IP의 Mini PC에 직접 SSH하는 것은 불가능합니다. WSL2에 GitHub self-hosted runner를 등록해 GitHub Actions job을 Mini PC가 직접 pull하는 방식으로 이 제약을 깔끔하게 해결했습니다.

이 패턴은 기업 온프레미스 배포에서도 동일하게 사용되는 표준 접근법입니다. 제약을 우회하는 설계 결정을 README에 명확히 기술한 점도 좋습니다.

✓
runtime 경로 / repository 경로 분리 잘된 점 ▾

Repository의 gitlab/은 placeholder로만 유지하고, 실제 GitLab 운영 데이터는 /home/gali/gitlab/ 고정 경로에 분리 보관합니다. Git push/pull에 GitLab 데이터가 포함되거나 CI workspace가 overwrite하는 사고를 방지하는 올바른 구조입니다.

✓
Grafana Provisioning — 대시보드 코드화 잘된 점 ▾

Grafana datasource와 dashboard를 provisioning/ YAML + JSON으로 코드화해 컨테이너 재생성 시에도 대시보드가 자동 복원됩니다. "클릭해서 설정한 것은 재현 불가"의 운영 안티패턴을 피한 설계입니다.

!
Monitoring image tag — latest 고정으로 재현성 저하 개선 포인트 ▾

MINI_PC_HOST는 GitHub Secrets로 주입해 workflow에 민감값 하드코딩을 방지했습니다. 반면 docker-compose.monitoring.yml의 prom/prometheus:latest, grafana/grafana:latest는 버전이 고정되지 않아 예상치 못한 업스트림 업데이트에 영향을 받을 수 있습니다.

운영 재현성을 위해 prom/prometheus:v2.52.0, grafana/grafana:11.0.0처럼 specific tag로 고정하는 것을 권장합니다.

!
N100 경량화 — 이미 튜닝됨, 추가 개선 방향 개선 포인트 ▾

GitLab Omnibus가 N100 16GB 환경에서 무겁다는 점을 인식하고, 이미 compose 환경변수로 puma['worker_processes'] = 1, sidekiq['concurrency'] = 5, postgresql['shared_buffers'] = "256MB"를 적용해 경량화했습니다.

추가 개선 방향으로는 Prometheus scrape_interval 조정(현재 default 15s → 60s로 늘려 메모리 부담 감소), Monitoring image tag 버전 고정, GitLab 자동 백업 스케줄 구성(gitlab_rails['backup_keep_time']) 등이 적합합니다.

!
docker-compose.full.yml — 0 bytes 미사용 파일 개선 포인트 ▾

docker-compose.full.yml이 0 bytes 빈 파일 상태입니다. 실제 배포 workflow에서는 이 파일을 참조하지 않으며, docker-compose.gitlab.yml과 docker-compose.monitoring.yml을 별도로 사용합니다.

사용하지 않는 빈 파일이 디렉토리에 남아 있으면 코드 리딩 시 혼란을 줍니다. 삭제하거나 README에서 미사용 파일임을 명시하는 처리가 필요합니다.
